## FINAL REPORT (executive synthesis — full sourced detail in the Appendix below)

### Introduction

**Methodology note:** this pass relied primarily on web search of vendor pricing pages, official docs, press coverage, and GitHub repositories, cross-checked against multiple independent sources where possible; several categories (hosted SaaS "AI employee" tools especially) are dominated by SEO/affiliate review sites rather than primary vendor documentation, and pricing figures in particular should be re-verified against the vendor's own current pricing page before any purchase decision, since 2026 has seen multiple mid-year pricing overhauls (Dust, Zapier, Salesforce) that make older secondary sources unreliable. Where only a single secondary source was found for a load-bearing claim, this is flagged explicitly rather than presented as settled fact.

This survey covers horizontal "AI workforce" / "AI company" / agent-orchestration platforms not already evaluated by the operator (Paperclip, OpenClaw, Hermes, NanoClaw, n8n, Windmill, Temporal, LangGraph, CrewAI). The operator wants a layer that holds strategy/goals, works unattended on a schedule, creates tasks/decisions for a human to approve (not the reverse), runs e-commerce operations through MCP tools, enforces a hard human-approval gate on money, and avoids vendor lock-in and API-only billing — strongly preferring Claude Code and Codex CLI on existing subscriptions, with API access as a fallback only. Every claim below is tagged **VERIFIED** (primary source), **REPORTED** (secondary source, not independently cross-checked), or **UNKNOWN**. Full citations for every claim are in the Appendix section of this same document, organized under the matching numbered headings.

### 1. Hosted platforms: uniformly disqualified by lock-in and API billing

Twenty hosted products were examined: Lindy, Relevance AI, Beam AI, Sintra, Artisan, Dust, Motion, Wordware, Gumloop, Zapier Agents, Make.com AI Agents, Notion Custom Agents, Asana AI Teammates, monday.com's "digital workforce," Linear Agent, Salesforce Agentforce, Microsoft Agent 365/Copilot, Google's Gemini Enterprise Agent Platform (formerly Agentspace), OpenAI Frontier, and Amazon Bedrock AgentCore. None supports running on a Claude Code or Codex CLI subscription — every one bills through its own credits, seats, or the underlying model API. This is a structural, not incidental, mismatch with the operator's core constraint (REPORTED across all twenty; several cross-confirmed via vendor pricing pages, tagged VERIFIED individually in the Appendix).

**Relevance AI** is the strongest hosted candidate on the goals/org-chart axis: it models a "Workforce" as named coworker roles (researcher, qualifier, drafter, reviewer, escalator) and supports MCP alongside 2,000+ integrations (REPORTED). But it has no OKR/strategy object, no confirmed enforced pre-spend approval gate, and bills via API-style "Vendor Credits" ($234-349/mo Team tier, REPORTED) — disqualifying on two of the three highest-weighted criteria.

**Dust** stands out as "one of the few workspace AI platforms" with a documented self-host option (REPORTED, single secondary source, unverified against Dust's own docs) and native MCP adoption, but its mental model is company-knowledge assistants, not a goals/org-chart/approval-gate product, and it bills on its own credit system.

**Salesforce Agentforce, Microsoft Agent 365, and Google's Gemini Enterprise Agent Platform** are enterprise governance/control-plane products (VERIFIED primary-source detail on each: Agentforce's per-org RBAC inheritance and Enterprise-Edition-bundled MCP access; Agent 365's GA as an agent-inventory/permissions control plane; Gemini Enterprise's per-seat MCP-building tiers) — all are deeply platform-native (Salesforce org, Microsoft 365/Entra, Google Cloud/Workspace) with no path to Claude/Codex CLI billing and high migration cost away from the operator's existing Supabase-based stack.

**OpenAI Frontier** (launched Feb 5, 2026, VERIFIED via TechCrunch/CNBC) is architecturally the closest hosted analog to what the operator wants — an "open platform" for governing agents "like employees" that claims to manage agents built outside OpenAI too — but it is an OpenAI product billed through OpenAI's enterprise agreements, which would reintroduce exactly the second-vendor API dependency the operator wants to avoid.

**Amazon Bedrock AgentCore** is infrastructure (Runtime, Gateway, Memory, Identity, Policy — 12 billable components, VERIFIED via AWS's own consumption pricing), not a company/goals product; its Gateway is fundamentally an MCP broker, useful as a substrate but requiring migration off Supabase/Hetzner and pure consumption billing.

Among workspace-native tools, **Notion Custom Agents** (shipped Feb 24, 2026, VERIFIED via Notion's own release notes) and **Linear Agent** (public beta March 2026, VERIFIED via Linear's own docs) are the most transferable patterns: both are scheduled/event-triggered, MCP-connected agents that create work items for a human — Notion reports running 2,800 such agents internally. Neither has a goal/OKR object or a money-approval gate, and neither runs on subscription-CLI billing, but both illustrate that "scheduled, MCP-connected, workspace-native agents that create tasks for humans" is now a mainstream, well-adopted pattern — the same shape the operator already built by hand.

### 2. Open source: three young projects are near-exact matches; the mature ecosystem lacks the "company" layer entirely

This category produced the most directly useful findings. A cluster of small, MIT-licensed 2026 projects were built by solo operators for precisely this problem:

**5dive** (github.com/5dive-ai/5dive, VERIFIED via primary repo/docs) is the closest match found in the entire survey. Its own tagline: "Run a company of AI agents on a server you own. Spin up named agents (claude, codex, grok…), put them on an org chart with a shared backlog, let them hand off work and ping your phone only when a human must decide." It has a real goal object (`5dive goal add` converts an outcome into a "guarded task graph" with dependencies and verification gates), an org chart (`5dive org set`, tracking whether handoffs stayed agent-to-agent with no human involved), and — critically — an explicit approval-gate primitive for money decisions (`5dive task need --type=approval --ask=... --options=...` sends tap-to-answer buttons to Telegram, with the core design principle being agents "work autonomously and ping your phone only when a human must decide"). It wraps Claude, Codex, Antigravity, Grok, Devin, Hermes, OpenClaw, OpenCode, and Pi CLIs, each as its own systemd-managed Linux user, and its installer explicitly expects "your own agent-CLI subscription or API key (Claude Pro/Max, OpenAI, etc.)" — a direct hit on the subscription-CLI requirement. It self-hosts on a 1GB Linux VM with SQLite (no external DB), is MIT with "no open-core" split, and provides audit trails (`5dive trace`, `5dive run events/logs/metrics`). Its two real gaps: no documented MCP-broker feature, and cost tracking is "best-effort" rather than a hard per-decision dollar ledger. It is also young — 55 GitHub stars, though the authors state "we run our own company on this."

**OpenGoat** (github.com/marian2js/opengoat, VERIFIED) has an even more explicit reporting-line hierarchy (`--manager --reports-to`) across Claude Code, Codex, Cursor, and other CLIs, but its task-creation model reads as agent-to-agent delegation rather than agent-to-human escalation, and it has no documented financial-approval gate, goal/OKR object, or scheduling primitive — a real hierarchy, but without the human-approval loop the operator specifically wants. MIT, 427 stars.

**OpenCompany** (github.com/zeenie-ai/OpenCompany, VERIFIED) integrates Claude Code CLI and Codex CLI as agent backends, has genuinely strong natural-language cron scheduling with 24-hour catch-up, and uses Temporal for durable execution — more production-grade than 5dive's systemd approach — but its financial-action support (a Stripe node with spend tracking) does not clearly document a blocking pre-spend approval gate, and its own framing is "bring your own API keys, or run models locally," putting API-key billing ahead of subscription-CLI billing in its primary framing even though Claude Code/Codex CLI integration exists. MIT, 857 stars, self-described "production-ready" (unverified independently).

The mature, well-funded OSS automation ecosystem tells the opposite story: **Dify** (149,000+ stars, VERIFIED-ish, bidirectional MCP since H1 2026), **Activepieces** (MIT, "largest open source MCP toolkit," 400+ integrations each doubling as MCP servers, VERIFIED-ish), **Agno/AgentOS** (41,000+ stars, native MCP+A2A, framework+runtime+control-plane stack), **Mastra** (TypeScript, bidirectional MCP), and the newly-merged **Prefect+Dagster+FastMCP** and **Kestra** orchestrators are all mature, genuinely strong on MCP connectivity and execution reliability — but **none of them has any goal/OKR object, org-chart-with-departments, or approval-gate primitive**. That layer would always need to be hand-built on top of any of them, which is exactly what the operator has already done in Habib OS's Supabase schema. **SuperAGI** is stalled with unaddressed security debt (REPORTED, excluded). **Flowise** is winding down after Workday's acquisition, with a code freeze July 29, 2026 and support ending Aug 31, 2026 (VERIFIED-ish, excluded for new bets). **AutoGPT Platform**'s most-developed components now sit under the source-available (not OSI-approved) Polyform Shield License, a meaningful lock-in concern the operator's criteria would flag. **CrewAI's** enterprise AMP/Factory tiers are priced and staffed ($60-120K/yr quoted, self-host needing a dedicated DevOps team per third-party estimates) for teams with capacity the operator explicitly does not have. **Letta/MemGPT** and **Agency Swarm** are relevant only as a memory substrate and an OpenAI-API-first framework respectively, neither a fit as the company layer itself.

### 3. Claude Code as orchestrator: already occupies the same category as 5dive — with the same gaps

The operator's current architecture (a git repo, cron/systemd, Claude Code/Anthropic SDK doing the reasoning, no packaged product) is not a compromise relative to a hosted platform — it is architecturally the same category as 5dive and OpenCompany: a thin coordination layer over Claude/Codex CLIs, self-hosted, with a human-approval surface. Claude Code itself has grown real native capability in 2026: three distinct scheduling mechanisms (`/loop` for in-session polling that expires after 3 days, VERIFIED; Desktop-app local Routines that need the app open and machine awake, VERIFIED primary docs; and Cloud Routines, shipped April 14, 2026, that run on Anthropic's own infrastructure regardless of device state, VERIFIED-ish cross-confirmed — functionally the built-in analog to the operator's cron/systemd design); subagents and Agent Teams (dynamic spawning of specialized Claude Code sessions, though explicitly shaped for software-engineering roles like planner/implementer/reviewer/QA, not business departments, REPORTED); 31 documented hook events as of Aug 8, 2026 that could technically implement an approval gate but are a general extensibility mechanism, not a purpose-built financial-approval primitive (VERIFIED-adjacent); and native, first-class MCP client support. Codex CLI's H1 2026 additions include "persistent Goals with token budgets" (REPORTED, single secondary source, unverified against OpenAI's own changelog) — potentially the single most relevant native feature found anywhere in this survey for the "holds strategy/goals" requirement, and worth direct hands-on testing before relying on the claim.

What neither CLI has natively: a goal/OKR object that persists and tracks progress across runs (Codex's claim aside, pending verification), a budget/spend ledger as a product feature, an approval-request UI/audit trail, an org-chart/departments abstraction, or a cross-run knowledge-compounding pipeline — all of which the operator has already hand-built in Supabase and Mem0. The realistic choice is therefore not "adopt a product instead of Claude Code" but "keep hand-rolling the goals/approval/org layer in Supabase+Mem0+Telegram (current path) vs. adopt 5dive's org-chart/task-graph/approval-gate primitives as a thinner layer that still shells out to the same CLIs" — the latter could reduce custom bookkeeping code while preserving the subscription-CLI/no-lock-in properties, at the cost of a 55-star dependency and re-plumbing MCP tool access and cost tracking to the operator's existing rigor.

### 4. Personal AI COO / chief-of-staff products: good at "when," not "why"

Motion's AI Task Manager (REPORTED) is the clearest example of automatic, proactive task/schedule management in this survey — it auto-schedules a day around deadlines/priorities/dependencies and flags at-risk tasks without being asked — but it only reschedules and flags pre-existing tasks; it does not originate net-new strategic tasks from a business goal (it would not, on its own, decide a SKU needs restocking). Reclaim, Sunsama, and Akiflow occupy a deliberate automation-vs-manual-control spectrum below Motion (REPORTED) and share the same ceiling: excellent calendar/task hygiene, no goal object, no MCP-based business operations, no money-approval gate.

OpenAI's ChatGPT Pulse — a dedicated proactive-briefing feature including "progress toward longer-term goals" — was retired around July 1, 2026 and folded back into plain Scheduled Tasks (VERIFIED-ish, multiple independent sources), a useful signal that a standalone "proactive AI" surface did not durably outcompete generic scheduling within OpenAI's own product. **Anthropic's Claude Cowork** (launched Jan 12, 2026, expanded to web/mobile July 2026, VERIFIED-ish via TechCrunch) is the most promising Anthropic-native candidate for the human-facing layer specifically: it can run scheduled tasks fully offline-of-device ("schedule a client prep task for 6am, close the laptop... Claude will work through email threads, Slack messages, meeting transcripts, and recent news, building the briefing document and leaving a follow-up email drafted for review") — a genuine "leave a draft for human review" pattern that matches the operator's "human approves, does not originate" preference, running on the same Claude subscription. It has no goal/OKR object, org chart, or approval-request table, and is aimed at general desktop work rather than e-commerce operations via MCP, but is worth prototyping as an inbox/review surface in front of the existing `approval_requests`/`notifications` tables, potentially alongside or eventually replacing parts of the Telegram bot.

### Recommendation

Do not migrate off the current Habib OS architecture to any hosted platform surveyed here — every one fails the subscription-CLI/no-lock-in constraint outright, and most also lack any goal/org-chart object. Continue building the goals/org-chart/approval-gate layer by hand in Supabase + Mem0 + Telegram as CLAUDE.md already specifies; nothing found here does that job better while respecting the lock-in and billing constraints. Do prototype two specific borrowings: (1) spike **5dive**'s org-chart/task-graph/Telegram-approval primitives as a possible replacement for the hand-rolled bookkeeping in `agent_runs`/`approval_requests` — it is MIT, no open-core, and wraps Claude/Codex CLIs on subscription billing exactly as required, though it is young (55 stars), undocumented on MCP, and weaker than the operator's own token-cost logging, so Supabase should likely remain the system of record regardless; (2) evaluate **Claude Cowork**'s "work in background, leave a draft for human review" pattern as a richer, same-subscription review surface alongside or instead of parts of the Telegram bot. Do not adopt MetaGPT/ChatDev/CAMEL (research artifacts), SuperAGI (stalled, security debt), Flowise (sunsetting), Agency Swarm or OpenAI Frontier (OpenAI-API-first), or CrewAI's enterprise AMP/Factory tiers (priced for teams with DevOps capacity the operator lacks). Dify and Activepieces are worth a second look purely as mature, self-hosted, MIT/Apache MCP tool-serving layers if the integration surface (payments, carriers, marketing tools) ever needs to grow faster than hand-rolling — without touching the goals/org-chart/approval design itself.

## 3. Claude Code itself as the orchestrator (no product at all)

The operator's current Habib OS architecture is, functionally, this option already: a git repo of Python scripts, cron/systemd on a Hetzner box, and (per the "Claude Code as orchestrator" framing) Claude Code/the Anthropic SDK doing the reasoning, with no packaged "AI workforce product" sitting on top. This section surveys what Claude Code and Codex CLI themselves now offer natively (as of Sept 2026) that could substitute for parts of a Paperclip-style product, and what's still missing.

### Claude Code native scheduling — three distinct mechanisms (VERIFIED, primary docs)
1. **`/loop`** — in-session, cron-backed recurring prompt execution inside a live terminal session. Minimum interval 1 minute, accepts natural-language times, but **expires after 3 days and does not persist across restarts or session close** — it is for active-development polling (watch a PR, watch a deploy), not unattended daily operations. [Better Stack — Claude Code /loop](https://betterstack.com/community/guides/ai/claude-code-loop/)
2. **Desktop scheduled tasks / local Routines** — configured in the Claude Code Desktop app (Routines → New routine → Local): name, prompt, frequency (hourly/daily/weekdays/weekly), model, permission mode. Persists across app restarts but **only fires while the desktop app is open and the machine is awake** — not suitable for a headless Hetzner VPS with no desktop session. VERIFIED (primary Claude Code docs). [code.claude.com/docs/en/desktop-scheduled-tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)
3. **Cloud Routines** — saved configurations (prompt + repo(s) + connectors) that run on Anthropic's own cloud infrastructure regardless of whether the operator's laptop/VPS is on. Shipped April 14, 2026 in research preview across all paid plans. VERIFIED (multiple cross-confirming sources, consistent launch date). [Medium — Rick Hightower, "The Two Claude Code Schedulers"](https://medium.com/@richardhightower/claude-code-the-two-claude-code-schedulers-that-run-on-your-machine-and-when-to-use-each-4cc7204222ca) — **this is the closest built-in Anthropic feature to what the operator's cron/systemd design does by hand**, and is itself the mechanism used elsewhere in this environment (the `create_trigger`/Routines tool family). It removes the need for the operator to run his own cron/systemd for the *scheduling* piece specifically, though it does not replace Supabase, Mem0, the executor, or the approval-request data model.

### Agent Teams, subagents, hooks (VERIFIED, primary + cross-confirmed docs)
- **Subagents**: each is a fresh Claude Code instance spawned by a lead session, with its own context window, tool permissions, and system prompt — directly analogous to the operator's three independent agent scripts (Inventory/PPC/Competitor), but spawned dynamically within one session rather than as separate cron-triggered processes. [Totalum — Claude Code subagents 2026 playbook](https://www.totalum.app/blog/claude-code-subagents-totalum)
- **Agent Teams**: coordinates multiple Claude Code sessions for larger work split by specialized responsibility (planning, implementation, test repair, security review, docs, migration, QA, release notes) — this is explicitly a **software-engineering-shaped** decomposition (built and marketed for coding work), not a business-operations org chart with goals/OKRs/departments. REPORTED, consistent across sources. [FlorianBruniaux/claude-code-ultimate-guide](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/agent-teams.md)
- **Hooks**: 31 documented hook events (as of Aug 8, 2026) across three cadences — per-session (SessionStart/SessionEnd), per-turn (UserPromptSubmit/Stop/StopFailure), and per-tool-call (PreToolUse/PostToolUse) — give deterministic control points that could implement an approval gate (e.g., a PreToolUse hook blocking a "place SP-API order" tool call pending a human signal), but this is a **general-purpose extensibility mechanism**, not a purpose-built financial-approval primitive; building the operator's `approval_requests` semantics on hooks alone would be a from-scratch engineering project, not a checkbox. VERIFIED (primary-adjacent, dated documentation reference). [blakecrosley.com — Claude Code Hooks Explained](https://blakecrosley.com/blog/claude-code-hooks-explained)
- **Headless mode**: Claude Code can run as a one-shot CLI process with no TTY, reusing the same settings/hooks/permission rules as interactive use — this is exactly the invocation style the operator's own `agents/*.py` design already assumes conceptually (though the operator's design calls the Anthropic Python SDK directly rather than shelling out to the Claude Code CLI itself). VERIFIED.

### Codex CLI (OpenAI) — comparable 2026 feature set (REPORTED, consistent across sources)
- H1 2026 additions: **persistent Goals with token budgets**, thread-level delegation to subagents, a plugin marketplace, browser use, encrypted remote execution, and a one-command import of Claude Code configuration (`AGENTS.md`-compatible). [Daniel Vaughan — Codex CLI in 2026](https://codex.danielvaughan.com/2026/03/27/codex-cli-in-2026-whats-new/)
- **"Persistent Goals with token budgets" is the single most relevant native feature found in this whole survey for the operator's "holds strategy/goals" requirement** — it suggests Codex CLI, unlike Claude Code, has started building a first-class goal object with a cost ceiling directly into the CLI product itself, not just task lists. This deserves direct hands-on verification (this claim rests on secondary blog coverage, not OpenAI's own changelog, so treat as REPORTED pending primary confirmation).
- As of CLI v0.149.0 (Aug 20, 2026): an interactive `codex agents` dashboard (search/start/open/rename/stop tasks), directory-management slash commands, and `codex queue` for messaging existing local/remote sessions — general multi-agent-session tooling, not business/company-shaped. VERIFIED (version-pinned primary-adjacent source).

### Assessment: does "Claude Code as orchestrator, no product" cover the brief?

**What it covers well:** unattended scheduling (via Cloud Routines), tool use via MCP (Claude Code is itself a first-class MCP client), specialized role decomposition (subagents/Agent Teams), and deterministic control points for gating (hooks) — plus, critically, it runs on the operator's **existing Claude subscription** with zero additional product to license, trust, or migrate off later. This is the maximum-portability, minimum-lock-in option in the entire survey almost by definition: the "product" is just markdown, Python, and standard Anthropic primitives, which is exactly the operator's stated anti-lock-in preference.

**What it structurally lacks, confirmed by the absence of any feature addressing these in the above research:**
- **No goal/OKR object.** Cloud Routines, subagents, and Agent Teams are all *execution* primitives — there is no native "strategy" or "objective" data type Claude Code tracks across runs; the operator's own Supabase schema (and Mem0's tiered observation→pattern→playbook system) is what supplies this, hand-built. Codex CLI's "persistent Goals with token budgets" (REPORTED) may be ahead of Claude Code here specifically and is worth testing.
- **No budget/spend ledger as a product feature.** The operator tracks token spend per agent run manually in `agent_runs`; neither Claude Code nor Codex ships a native per-task-graph dollar budget UI (Codex's "token budgets" claim aside, unverified).
- **No approval-request UI/audit trail as a product feature.** Hooks can technically implement a gate, but there is no equivalent of Paperclip's (or the operator's own) `approval_requests` table + Telegram bot + dashboard — that is 100% custom work in the "Claude Code as orchestrator" model, same as it already is in Habib OS today.
- **No org chart / departments abstraction.** Agent Teams is explicitly software-engineering-role-shaped (planner, implementer, reviewer, QA), not "Inventory Department, PPC Department, Competitor Intel Department" — mapping business departments onto it would be a naming convention, not a supported concept.
- **No cross-run persistent memory/knowledge-compounding system built in** — this is precisely why the operator's plan layers Mem0 on top; Claude Code/Codex have no native equivalent of the three-tier observation→pattern→playbook promotion pipeline.

**Verdict for Section 3:** "Claude Code as orchestrator with no product" is not a compromise relative to Paperclip or 5dive so much as it **is** the same category as those two (all three are "thin coordination layer over Claude Code/Codex CLI, self-hosted, MIT/first-party, Telegram-or-similar as the human surface") — the operator's own repo already occupies this position. The realistic choice is not "adopt a product instead of Claude Code," it's "keep hand-rolling the goals/approval/budget/org layer in the existing Supabase+Mem0+Telegram stack (current path), vs. adopt 5dive's org-chart/task-graph/approval primitives as a thinner layer that still shells out to the same Claude/Codex CLIs" — the latter could plausibly reduce custom code for org-chart bookkeeping and Telegram approval UI while keeping 100% of the subscription-CLI/no-lock-in properties the operator wants, at the cost of adopting a 55-star dependency and re-plumbing MCP tool access and cost tracking to match the operator's existing rigor.

## 4. Personal AI COO / "chief of staff" products — what good "creates tasks for me" looks like

The brief asks specifically what "creates tasks for me" looks like when done well, and whether such a layer could sit on top of the Habib OS repo as the human-facing surface. Findings:

### Motion (revisited as the reference case)
- Motion's "AI Task Manager" is the clearest example in this survey of proactive, automatic task/schedule management: it analyzes deadlines, priorities, dependencies, durations, and auto-schedules the day while flagging at-risk tasks before they slip — the human never has to ask, it just appears rescheduled with a flag. REPORTED, consistent across sources (see Section 1 for pricing/sourcing detail). This is "good" proactive task creation in the *personal productivity* sense: the system decides *when* pre-existing tasks happen and surfaces conflicts, but it does not originate net-new strategic tasks from a business goal the way the operator wants (e.g., it would not on its own decide "SKU-017 needs a restock" — that decision has to already exist as an entered task/project).

### Reclaim.ai / Sunsama / Akiflow — spectrum of automation vs. control
- These three sit on a deliberate automation-vs-manual-control spectrum: Reclaim automates calendar defense of existing habits/focus-time; Motion goes furthest on full auto-scheduling; Sunsama is a "do fewer things, deliberately" daily planning ritual (explicitly *not* automatic); Akiflow is a fast manual command-bar for people who want maximum control and speed over automation. REPORTED, cross-confirmed by multiple comparison pieces. [Temporal.day comparison](https://temporal.day/blog/motion-vs-reclaim-vs-clockwise-vs-akiflow-vs-sunsama)
- None of the four natively runs business operations via MCP tools, none has a money-approval gate, and none holds a strategic-goal object that spins off tasks — they are calendar/task hygiene tools, one layer below what the operator needs. They illustrate the ceiling of "personal productivity AI" circa 2026: excellent at *when*, not *why* or *what should exist*.

### Lindy "chief of staff" framing
- Lindy markets itself as (among other things) a personal AI executive assistant reachable over iMessage/web that handles email/meetings and runs multi-app workflows; it has shipped role-specific templates (an "AI CMO" template was found) but no distinct, named "chief of staff" template was confirmed in this research pass. REPORTED, low confidence on the specific template claim — treat as UNKNOWN whether a literal "chief of staff" template exists as of Sept 2026; the broader "AI teammate" positioning is confirmed (see Section 1).

### OpenAI ChatGPT: Pulse → Scheduled Tasks, and Agent mode
- **ChatGPT Pulse** (proactive nightly synthesis of memory/chat history/feedback into personalized updates, including "progress toward longer-term goals") was **retired around July 1, 2026 and folded into Scheduled Tasks** — i.e., OpenAI tried a dedicated "proactive AI" surface and consolidated it back into the general scheduling primitive within roughly a year. VERIFIED-ish (multiple sources independently report the same retirement date and reason). [techjacksolutions.com](https://techjacksolutions.com/ai-brief/agentic-ai-news-openai-launches-scheduled-tasks-in-chatgpt-a/) This is a useful signal: a standalone "proactive briefing" feature did not durably outcompete plain scheduled-task automation, at least inside ChatGPT's product.
- **ChatGPT Agent mode** (from July 2025, still current) works like "a coworker that lives inside ChatGPT" — given tool access (Slack, Outlook, etc.) it runs in the background on a plain-language brief. REPORTED. No goal/OKR object, no org chart, no financial approval gate, no MCP-first design confirmed; single-agent, not a company.

### Anthropic Claude Cowork (launched Jan 12, 2026; expanded to web/mobile July 2026)
- Built on the same foundations as Claude Code, exposed as a "computer agent" for non-technical desktop tasks — give it a folder + plain-language instructions (fill out an expense report from receipt photos, write reports from notes, reorganize folders). VERIFIED-ish, launch date and framing cross-confirmed by TechCrunch and Anthropic-adjacent coverage. [TechCrunch — Claude Cowork](https://techcrunch.com/2026/07/07/the-coding-agent-wars-are-spilling-into-the-rest-of-the-office-claude-cowork/)
- **Background execution with no device online** is the standout feature relevant to this survey: "you can schedule a client prep task for 6am, close the laptop, and Claude will work through email threads, Slack messages, meeting transcripts, and recent news, building the briefing document and leaving a follow-up email drafted for review" — this is close to genuine proactive task-drafting-for-a-human-to-approve, running on Anthropic's own infrastructure under the operator's existing subscription. VERIFIED-ish (same source cluster). Task queueing/parallel execution ("queue multiple tasks, execute them in parallel") moves it toward an autonomous-coworker model rather than turn-based chat.
- **Fit assessment**: Cowork is squarely aimed at *general desktop/office work* for non-technical users, not e-commerce operations via MCP against Supabase/SP-API, and it has no goal/OKR object, org chart, approval-request table, or budget ledger — but as a **human-facing task-inbox/approval surface** sitting in front of a backend that already does the reasoning (exactly the layer the brief asks about in point 4), Cowork is architecturally the most promising Anthropic-native candidate found: it already knows how to "leave a draft for review" rather than act unilaterally, which is the human-approves-doesn't-originate pattern the operator wants, and it runs on the same Claude subscription rather than a separate bill.

### Section 4 verdict
No product surveyed here does "manage my business's goals and generate my task list" end-to-end for an e-commerce operation. The best *pattern* for "creates tasks for me, done well" is Motion's automatic day-rescheduling-plus-risk-flagging combined with Claude Cowork's "work in the background, leave a draft for human review" behavior — neither is a fit as the whole system, but Cowork in particular is worth prototyping as the **inbox/approval-review layer** in front of the existing Habib OS Supabase `approval_requests`/`notifications` tables, since it already speaks Anthropic's subscription billing and Claude Code's execution model, and could plausibly replace or complement the Telegram bot as a richer review surface without adding a second vendor.

## Recommendation

**Do not migrate off the current Habib OS architecture to any hosted platform found in this survey.** Every hosted "AI workforce" product examined — Lindy, Relevance AI, Beam AI, Sintra, Artisan, Dust, Salesforce Agentforce, Microsoft Agent 365, Google's Gemini Enterprise Agent Platform, OpenAI Frontier, Amazon Bedrock AgentCore — fails the subscription-CLI/no-lock-in criterion (weight 15%) outright, and most also fail the goals/org-chart criterion (weight 20%) by having no first-class strategy object at all. This confirms the operator's instinct: hosted "AI company" products are built to be the vendor, not to be a thin layer over the operator's own CLI subscriptions.

**Do continue building the goals/org-chart/approval-gate layer by hand in Supabase + Mem0 + Telegram** as the CLAUDE.md architecture already specifies — nothing surveyed here does that job better while satisfying the lock-in and subscription-CLI constraints. The Phase 6 (Knowledge Compounding) and Phase 7 (Dashboard) work already planned remains the correct next investment, not a platform swap.

**Do prototype two specific borrowings, in priority order:**
1. **5dive's org-chart/task-graph/Telegram-approval primitives** (github.com/5dive-ai/5dive) are worth a hands-on spike specifically for the *bookkeeping* the operator is currently hand-rolling in `agent_runs`/`approval_requests`/the Telegram bot — it is MIT, no open-core, wraps Claude/Codex CLIs on subscription billing exactly as the operator wants, and its `goal add → guarded task graph → org chart → Telegram approval (including money) → audit trail` pipeline is structurally close to a pre-built version of Sections 6-9 of the operator's own CLAUDE.md. Treat it as a **library to borrow patterns/code from, or a thin coordination layer to adopt for the org-chart/approval UI specifically**, not a wholesale platform migration — it is young (55 stars), does not document MCP support, and its cost tracking is weaker than the operator's own token-spend logging, so Supabase would likely still need to remain the system of record for financial/audit data.
2. **Claude Cowork's "work in background, leave a draft for human review" pattern** (Anthropic-native, ships on the same subscription) is worth evaluating as a richer human-facing review surface that could sit alongside or eventually replace parts of the Telegram bot's approval UI, since it already implements the human-approves/doesn't-originate interaction model natively and requires no new vendor relationship.

**Do not adopt** MetaGPT/ChatDev/CAMEL (research artifacts, not production-shaped for this domain), SuperAGI (stalled, security debt), Flowise (sunsetting), Agency Swarm or OpenAI Frontier/AgentKit (OpenAI-API-first, works against the operator's Anthropic-subscription-first preference unless the operator specifically wants Codex-CLI-only agents), or CrewAI's enterprise AMP/Factory tiers (priced and staffed for teams with DevOps capacity the operator does not have).

**Worth a second-order look, as infrastructure rather than as the "company" layer itself:** Dify and Activepieces are the two most mature, fully self-hosted, MIT/Apache-licensed platforms with genuinely strong bidirectional MCP support — if the operator ever needs a large pre-built library of MCP-exposed integrations (payment processors, shipping carriers, marketing tools) faster than hand-rolling them, either could serve as an MCP tool-serving layer behind the existing agents without touching the goals/org-chart/approval design at all. Agno and Mastra are similarly strong as underlying agent-runtime substrates (both ship native MCP and production-oriented control planes) if the Python agent scripts ever outgrow direct Anthropic-SDK calls, though neither offers subscription-CLI billing and both would need the same custom goals/approval layer built on top that the operator already has.
