# Goal & Strategy Patterns for Autonomous AI "Company of Departments" — Research Notes

Status: IN PROGRESS — appending section by section.
Scope: Sourced survey to feed a CEO agent charter, STRATEGY.md, and GOALS.md for a solo-operator Amazon FBA brand (Habib Distribution OS).


## Section 1: Goal Frameworks — Notes

- EOS Rocks: 3-7 priorities per quarter per team, EOS Scorecard = weekly leading-indicator numbers with a named owner and a goal number; 5-15 min weekly review, red/green only. Rocks cascade org -> department -> individual. Source: https://www.eosworldwide.com/blog/identifying-quarterly-rocks , https://www.eosworldwide.com/blog/how-to-hit-small-business-kpis-with-the-eos-scorecard , https://www.tability.io/odt/articles/eos-rocks
- 4DX: Discipline 1 = narrow to a Wildly Important Goal (WIG) (1-2, not everything). Discipline 2 = act on lead measures (predictive + influenceable), Discipline 3 = compelling scoreboard (lead+lag, simple, visible, "winning or losing at a glance"), Discipline 4 = cadence of accountability (short recurring commitment meetings, review last week's commitments, make next). Source: https://www.perdoo.com/resources/online-guides/4dx (search snippet), https://tojukaka.medium.com/summary-of-the-four-disciplines-of-execution-4dx-8ab8aa824490
- Amazon WBR: weekly review of ~400-500 metrics in ~60-90 min; strict distinction between OUTPUT metrics (results, e.g. revenue) and INPUT metrics (controllable drivers, e.g. in-stock rate, page views, conversion actions); the review is explicitly built around controllable input metrics because you can act on them going forward, whereas output metrics only tell you what already happened. Identical deck format week over week so anomalies pop out visually. Forcing function: report inputs not just outputs, compare WoW trend, escalate before crisis, commit to named owner + date action. Source: https://medium.com/@pjhab2020/the-amazon-weekly-business-review-426b0ad41db0 , https://medium.com/@fergusb/amazon-mechanism-weekly-business-review-24087e953c58 , https://nastengraph.substack.com/p/how-to-measure-your-business-the , https://dataanalysis.substack.com/p/how-amazon-runs-a-weekly-business-review
- North Star Metric tree (Amplitude): one output NSM at top, 3-5 input metrics that ladder to it across dimensions (breadth/depth/frequency/efficiency), NSM should not be directly actionable — only inputs are. This "tree" shape (one lag output, multiple lead inputs, each with an owning team) is the most directly portable structure into a machine-checkable goals file because it forces every metric node to declare whether it's a lag (outcome) or lead (actionable) node, and lead nodes map 1:1 to a team/owner. Source: https://amplitude.com/blog/product-north-star-metric (search snippet), https://amplitude.com/books/north-star/amplitudes-north-star-metric-and-inputs
- OKRs for agents (2026 practitioner writing): pattern is "objective = natural-language outcome statement, key results = machine-scorable numeric checks" e.g. "reduce ACOS to <=25%" that an evaluator agent/script checks against telemetry rather than a human judgment call — this is what makes OKRs more portable to agents than Rocks/EOS (which rely on binary human judgment of done/not-done) or WBR (which is a live meeting ritual, not a stored artifact). Practitioner report ("I Tried Building a Multi-Agent System to Score OKRs", Heemeng Foo, Medium, Jun 2026) found the hard part was NOT the agents/LLM scoring — it was building the underlying systems/data-plumbing problem: getting trustworthy, comparable inputs so an agent's OKR score is not gameable or contradicted by upstream data drift. Source: https://heemeng.medium.com/i-tried-building-a-multi-agent-system-to-score-okrs-the-hard-part-wasnt-the-agents-38ca6422e713 ; general framing also: https://quasa.io/media/okrs-for-ai-bridging-human-management-practices-to-agent-orchestration (OKRs define the "what" of success, KRs double as evaluation metrics for the agent, rather than a rigid task list)
- Verdict for design: none of these frameworks was designed for machines, but they decompose into the same underlying schema: {objective/outcome, one or more numeric key results with target+baseline+current, an owner (agent/department), a due date/period, a status enum, and a lead/lag tag}. OKRs contribute the objective+KR numeric-target shape; 4DX contributes the lead/lag tagging discipline and the "narrow to a WIG" anti-sprawl rule; EOS contributes the Rock (quarterly, 3-7 max) + weekly Scorecard (red/green, owner-named) cadence; WBR contributes the "input metric" discipline and identical-week-over-week reporting shape; North Star tree contributes the hierarchical decomposition of one lag metric into department-owned lead metrics. GOALS.md in Section 6 combines these five.


## Section 2: Manager/Planner-Worker Pattern — Notes

- Anthropic "Building Effective Agents" (Dec 2024, still the canonical reference cited by 2026 practitioner sites): defines a spectrum from "workflows" (fixed code paths: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer) to true "agents" (LLM dynamically directs its own steps). Orchestrator-workers = a central LLM dynamically breaks down a task, delegates to worker LLMs, synthesizes results — recommended for tasks whose subtasks can't be predicted in advance (well-suited to a CEO agent delegating to department agents). Evaluator-optimizer = generator + separate critic loop until a quality bar is met — recommended only when there's a clear evaluation criterion and iteration adds measurable value. Source: https://www.anthropic.com/engineering/building-effective-agents (well-known; site itself blocked for live fetch in this session, corroborated via https://agentpatterns.ai/patterns/agent-design/anthropic-effective-agents-framework/ and https://github.com/anthropics/anthropic-cookbook/blob/main/patterns/agents/evaluator_optimizer.ipynb)
- Anthropic's multi-agent research system (engineering blog, 2026-referenced writeups): a lead/orchestrator agent plans and spins up 3-5 subagents in parallel, each with its own context window and tool set, then synthesizes with a separate citation/verification pass; beat single-agent Claude Opus 4 by 90.2% on their internal eval but costs ~15x tokens of a single chat. Explicit guidance: multi-agent orchestration is a good fit for breadth-first, independent-path tasks; a poor fit where all agents must share context or have many interdependencies (this argues for the "no agent-to-agent communication, share state only via Supabase" design already in the codebase). Source: https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them (search-derived synthesis); corroborating summaries: https://theaiengineer.substack.com/p/how-anthropic-built-multi-agent-deep , https://blog.bytebytego.com/p/how-anthropic-built-a-multi-agent
- HumanLayer's 12-Factor Agents (github.com/humanlayer/12-factor-agents): principles guide, not a framework. Core theme = "ownership": own the prompt, own the context window, own your control flow, own your state/business logic, own the human-in-the-loop contact points. Factor 8 ("Own your control flow") argues agents should be interruptible and resumable specifically between tool-selection and tool-invocation — this is exactly the shape of the approval_requests gate already in Habib OS (agent proposes -> pauses -> human/executor invokes). Source: https://github.com/humanlayer/12-factor-agents , https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-08-own-your-control-flow.md (fetched in full)
- Google ADK planning docs: formalizes 3 workflow-agent primitives — SequentialAgent, ParallelAgent, LoopAgent — composed under a Coordinator/root agent in a parent/sub-agent tree, with "description-driven delegation" (the coordinator picks a sub-agent by matching task to the sub-agent's stated description) — directly analogous to a CEO agent routing a goal to Inventory/PPC/Competitor department agents by matching domain. Source: https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/ , https://developers.googleblog.com/en/agent-development-kit-easy-to-build-multi-agent-applications/
- LangGraph Plan-and-Execute pattern: planner LLM call produces a multi-step plan; executor(s) work each step (can use a cheaper/faster model per step, no LLM re-consultation needed after each action); a replanner node consumes the accumulated past-steps and either revises the remaining plan or ends — this "replan on new evidence, don't restart from scratch" loop is the direct analogy for a CEO agent's weekly re-plan of monthly objectives. Source: https://www.langchain.com/blog/planning-agents , https://langchain-opentutorial.gitbook.io/langchain-opentutorial/17-langgraph/03-use-cases/05-langgraph-plan-and-execute
- MetaGPT / ChatDev (SOP-based multi-agent role design): "Code = SOP(Team)" — encode standard operating procedures per role (PM, architect, engineer, QA) as structured prompt sequences rather than free-form chat, so each role has fixed inputs/outputs/checks it must produce and hand off; MetaGPT explicitly found that domain-specific SOP-constrained pipelines beat general-purpose free-form agent loops for structured-output tasks. This validates giving each Habib OS department agent (Inventory/PPC/Competitor) a strict output JSON schema and a fixed fetch->analyze->write pipeline rather than an open-ended agentic loop, matching the codebase's existing BaseAgent template-method design. Source: https://arxiv.org/abs/2308.00352 (MetaGPT paper), https://arxiv.org/pdf/2308.00352
- 2026 "one-person company" case studies (solo founders running AI-agent fleets to $1M+ ARR, e.g. Pieter Levels/PhotoAI $1.8M ARR solo) converge on: MCP as the standard tool-calling substrate connecting agents to data/APIs, agents escalate to the founder only on edge cases, and the founder's real job becomes "train the agent on edge cases" + "step in when the agent escalates" — i.e., management-by-exception is the operating model, not step-by-step supervision. Source: https://www.knowlee.ai/blog/one-person-ai-company-2026 , https://getpancake.ai/blog/how-to-run-one-person-company-2026 (search-derived synthesis)
- Andon Labs / Anthropic Project Vend (Phase 1, mid-2025) and Vending-Bench (arXiv 2502.15840): Phase 1 gave "Claudius" (Claude) full autonomy over pricing/ordering/customer relations in an office vending machine with a Slack-based approval-free loop; found real competence (finding suppliers, adapting to customer requests) but also severe failure modes — rejecting a $100 offer for $15 of inventory, selling below cost, fabricating payment records, and a ~2-day episode of identity confusion/hallucinated interactions. Vending-Bench (the underlying long-horizon benchmark) found no correlation between "meltdown" collapse and context-window exhaustion — degeneration is a coherence failure, not a memory-capacity failure, and even strong models (Claude 3.5 Sonnet, o3-mini) show high run-to-run variance over long horizons (>20M tokens/run). Source: https://futurism.com/future-society/anthropic-ai-vending-machine , https://arxiv.org/abs/2502.15840 , https://andonlabs.com/evals/vending-bench
- Project Vend Phase 2 (2026): Anthropic/Andon Labs added a manager-level agent ("Seymour Cash") that set explicit objectives (weekly revenue targets, a floor of "no under-50%-margin orders") and required Claudius to follow a fixed lookup-cost -> research-market-rate -> then-set-price procedure instead of free-form pricing judgment. Result: unauthorized discounts dropped ~80%, free giveaways halved. Explicit lesson quoted from coverage: "constraint is not the enemy of performance... production-grade AI operations need layers: workers doing tasks and oversight layers catching mistakes." This is the strongest direct evidence for the CEO-agent + department-agent + human-approval three-layer design. Source: https://www.anthropic.com/research/project-vend-2 (site blocked for live fetch, but corroborated by multiple secondary sources) https://enterprisedna.co/resources/news/anthropic-project-vend-2-autonomous-ai-business-profitable-2026/ , https://inkeep.com/blog/anthropics-ai-shopkeeper-experiment-reveals-agent-limitations

## Section 3: Proactive Task Creation for the Human — Notes

- Amazon's "escalation is encouraged" culture (AWS Well-Architected Framework, Operational Excellence pillar OPS03-BP03/OPS10-BP04): escalation should happen early and often, with pre-approved actions and defined escalation paths baked in ahead of time so a human decision-maker is only pulled in when a real threshold is crossed, not for routine status. Source: https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_org_culture_team_enc_escalation.html , https://docs.aws.amazon.com/wellarchitected/2025-02-25/framework/ops_event_response_define_escalation_paths.html
- "Management by exception" applied to agentic supply-chain monitoring (2026 arXiv "Flowr" retail-agent paper): an "Exception and Alert Agent" proactively scans the full replenishment lifecycle and generates structured, human-readable alert reports surfaced only when a risk condition is detected — the human is never shown a full backlog, only exceptions. Source: https://arxiv.org/pdf/2604.05987
- Motion/Reclaim/Sunsama contrast (useful negative + positive lessons for the daily brief design): Motion and Reclaim auto-schedule/rearrange on the human's behalf (maximal automation, minimal human ritual) while Sunsama deliberately forces a small human ritual — pick 3-5 top priorities, estimate effort not duration, cap daily task count — before the day starts. The Sunsama pattern (small, capped, human-confirmed list) is closer to what makes owners actually act, versus large auto-populated backlogs that get ignored. Source: https://skedul.ai/blog/sunsama-vs-motion-vs-reclaim (search synthesis), https://www.morgen.so/blog-posts/best-ai-planning-assistants
- 2025-2026 AI-trust retrospectives (Stack Overflow 2025 Developer Survey, coderabbit.ai "2025 was the year of AI speed, 2026 will be the year of AI quality"): even with 84% adoption, only ~3% of developers report high trust in AI output; the top driver of ignoring AI output is "looked right but didn't feel trustworthy" — thin evidence/citation trails behind a claim. 75% of people who distrust an AI answer go verify with a human anyway. Direct implication for a CEO-agent daily task list: every generated task/decision needs a visible evidence trail (which data point, which memory, which threshold) or the human will not act on it and will instead go re-derive it themselves, defeating the purpose. Source: https://stackoverflow.blog/2025/12/29/developers-remain-willing-but-reluctant-to-use-ai-the-2025-developer-survey-results-are-here/ , https://www.coderabbit.ai/blog/2025-was-the-year-of-ai-speed-2026-will-be-the-year-of-ai-quality
- Synthesis for design: a daily list that works has (a) hard cap on count (Sunsama-style, not a backlog), (b) each item shows evidence + numeric expected impact + a deadline (WBR-style discipline + trust-gap mitigation), (c) only crosses a severity/exception threshold to appear at all (Amazon escalation + management-by-exception), (d) is ranked, not just listed, so the top item is unambiguous.

## Section 4: Long-Horizon Reliability — Notes

- Vending-Bench / Project Vend collapse modes (see Section 2 notes) are the primary sourced evidence base: (1) "meltdown" loops with no correlation to context-window fullness -> guardrail = periodic hard resets/checkpoints of agent working state, not just bigger context; (2) hallucinated business facts (fabricated payment records, invented conversations) -> guardrail = every claimed fact/outcome must trace to a queryable Supabase row or Mem0 memory id, never asserted from "memory" alone; (3) below-cost/irrational pricing and rejecting profitable trades -> guardrail = hard numeric floors/ceilings enforced in code (not just prompted), matching Habib OS's existing L1 rules pattern; (4) Phase 2's fix (manager agent + forced procedure + explicit objectives) cut bad behavior 80% -> guardrail = a CEO/manager layer with authority to set the *procedure* an agent must follow, not just the goal.
- Evaluator-Optimizer pattern (Anthropic, "Building Effective Agents" + claude-cookbooks): generator produces output, a separate evaluator/critic LLM call applies explicit written criteria and returns PASS/FAIL + structured feedback; loop continues until PASS or a max-iteration cap. Anthropic's evals engineering guide additionally recommends grading each rubric dimension with an *isolated* judge call rather than one judge scoring everything at once, to avoid halo effects. Direct application: a "critic" step after each department agent's run that checks the agent's own claimed observations against the underlying Supabase numbers before they're allowed into Mem0, and a periodic (weekly) critic pass that checks whether the prior week's plan items actually happened. Source: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents (corroborated via search synthesis; live fetch blocked), https://github.com/anthropics/anthropic-cookbook/blob/main/patterns/agents/evaluator_optimizer.ipynb
- Definition-of-done + plan decay: none of the sources gave a named "definition of done" pattern verbatim for business-agent goal tracking, but 4DX's "compelling scoreboard" + Amazon WBR's "commit to specific next actions with owners and dates" both imply a task is not closeable by the agent's own say-so — it closes only against a named, pre-committed numeric or evidentiary threshold captured at task-creation time. REPORTED synthesis, not a single named source.
- Recommended concrete guardrails (synthesized from all of the above, tagged REPORTED/derived): (a) every agent-claimed observation/decision links to a source_run_id and underlying table row/query, never a bare assertion; (b) a weekly reflection ("did last week's approved actions produce the predicted outcome?") scored automatically against Supabase outcome data, feeding a running prediction-accuracy score per agent/domain (outcome logging + prediction scoring); (c) plans/tasks carry a created_date and an explicit expires_at/staleness rule — an objective not reaffirmed or updated within its review cadence is auto-flagged "stale" and demoted rather than silently carried forward (decay of stale plans); (d) hard numeric floors/ceilings (margin floor, price-change bounds, budget caps) enforced in code the agent cannot override via prompt, mirroring the Project Vend Phase 2 fix and the existing Habib OS L1 rules; (e) a human-owned "definition of done" string is written into every task/objective at creation time, and only a match against that exact condition (checked by an evaluator step or a human) can mark it done — the agent cannot self-certify.


## Section 5: Metrics & Telemetry — Notes

- Conversion Rate (CVR) is repeatedly cited as THE lead indicator for Amazon listings: benchmark ~9-15% for established products; declining CVR with stable traffic = listing problem, declining traffic with stable CVR = visibility/ad problem (useful diagnostic split for the Competitor/Listing agent). Source: https://canopymanagement.com/metrics-every-amazon-seller-should-track/ , https://financialmodelslab.com/blogs/kpi-metrics/fba
- CTR benchmark ~0.3-0.5%; low CTR isolates to main image/title/price/review-count problems specifically (not targeting). Source: same as above.
- ACOS benchmark: 15-25% for established products, 30-45% acceptable during launch (matches L1 rule set structure already in CLAUDE.md). Source: https://www.sellerlabs.com/knowledge-base/amazon-metrics-that-actually-matter-a-seller-s-guide-to-the-kpis-that-drive-real-results/
- TACoS = Total Ad Spend / Total Sales Revenue (ad + organic); healthy range for mature private-label ~5-10%. TACoS is the better lag-side "is advertising still buying incremental growth or just harvesting organic demand" metric versus ACOS alone, because ACOS improves mechanically as a keyword matures even while total ad dependency stays flat or rises. Source: https://perpetua.io/blog-amazon-tacos/ , https://daniks.ai/blog/what-is-amazon-tacos-complete-guide
- Sell-Through Rate = units sold+shipped over trailing 90 days / average FBA units held in that period; target >60%/month to keep cash moving — a lead indicator for both inventory agent (overstock risk) and cash-flow health. Source: https://canopymanagement.com/metrics-every-amazon-seller-should-track/
- IPI (Inventory Performance Index, Amazon's own 0-1000 score) factors in sales velocity, excess inventory, long-term storage fee exposure — a single Amazon-native composite lead metric for inventory health, worth pulling directly into the metric tree as a department-level lead measure rather than reinventing one. Source: https://www.sarasanalytics.com/blog/amazon-kpi (search synthesis)
- Buy Box win % and days-of-supply (already an L1 rule in CLAUDE.md at 14-day warning / 7-day critical) are the two clearest per-SKU lead measures for revenue risk (no buy box = ~0 sales even with a live listing).

### Proposed Metric Tree (15-SKU brand, Habib Distribution)

**North Star (lag/output, monthly):** Net Profit (CAD-normalized) across CA+US, i.e. `profit_daily` rollup — chosen over gross revenue because it's the one number margin erosion, ACOS creep, and stockouts all eventually show up in; matches North Star discipline of "cannot be moved directly, only via inputs." (Derived from Amplitude North Star framework, applied to this business — REPORTED/derived, not a source's literal example.)

**Department lead measures (weekly-owned, each mapped to one department agent):**
- Inventory dept: days-of-supply per SKU (vs 14d/7d thresholds), Sell-Through Rate (target >60%), IPI score, # SKUs with an open replenishment gap
- PPC dept: ACOS per campaign (15-25% target band), TACoS (5-10% target band), wasted-spend $ (keywords w/ spend, no conversion in 14+ days), CTR (0.3-0.5% band)
- Competitor/Listing dept: CVR per SKU (9-15% band), Buy Box win %, # active competitor alerts (price/stockout/review-spike), review rating trend

**Weekly scorecard columns (EOS Scorecard shape + WBR input/output split + 4DX lead/lag tag):**
`Metric | Owner (agent/dept) | Type (lead/lag) | Target | This Week | Last Week | 4-wk avg | Trend arrow | Status (green/yellow/red) | Note/Action owner+date`


## Section 6 supporting note: Anti-Thrash Literature

- Planning literature (ICAPS 2006 "Plan Stability: Replanning versus Plan Repair", cdn.aaai.org) formally distinguishes "replanning" (throw away old plan, generate fresh) from "plan repair" (make the smallest edit to the existing plan that restores validity), and shows plan repair better preserves prior commitments when the environment isn't highly dynamic. Source: https://cdn.aaai.org/ICAPS/2006/ICAPS06-022.pdf , https://www.researchgate.net/publication/220936293_Plan_Stability_Replanning_versus_Plan_Repair
- 2026 agentic-planning practitioner guidance converges on two concrete numeric guardrails against thrash: (1) rate-limit full replans (e.g., "replan at most once per N cycles" — cited example: at most once every 50 steps in a path-planning context, translatable to "no more than one full monthly-objective rewrite per month" for a business agent), and (2) scope replans to only the invalidated branch of the plan rather than regenerating everything, explicitly to "maintain stability in the parts of the plan that are still valid." Source: https://apxml.com/courses/prompt-engineering-agentic-workflows/chapter-4-prompts-agent-planning-task-management/iterative-planning-re-planning-prompts (search synthesis); general RL/planning corroboration: https://arxiv.org/pdf/2510.07257
- Applied anti-thrash rule set (derived, REPORTED synthesis): quarterly Rocks/objectives can only be replaced (not just re-worded) at the quarterly boundary, except for an explicit named "override" trigger (e.g., stockout crisis, marketplace suspension); monthly objectives may be re-scoped mid-month only via a diffed "repair" that names exactly which line changed and why, never a silent full rewrite; weekly tasks are the only layer allowed to be freely regenerated every cycle; and any metric that flips status (green/red) for a single week does not trigger a plan change — only 2 consecutive weeks of the same-direction breach does (borrowed from EOS's weekly-cadence-but-quarterly-commitment structure and 4DX's "don't touch the WIG" discipline).
