## 1. Object Model: company, board, goals, projects, issues, agents, heartbeats, approvals, budgets

**VERIFIED** — from `docs/guides/welcome/key-concepts.md`, `docs/guides/welcome/glossary.md`, `docs/api/goals-and-projects.md`, `docs/guides/projects-workflow/goals.md`, `docs/guides/projects-workflow/projects.md` (paperclip-docs repo), and `docs/companies/companies-spec.md` (paperclip repo).

**Company**: "A self-contained AI organisation with a single goal, a team of agents, a task board, and a budget." Companies are isolation boundaries — separate goals, agents, tasks, budgets. Every object in Paperclip belongs to exactly one company.

**Board Operator**: the human owner — "the founder, the board, and the ultimate authority." Sets goals, reviews approvals, manages budgets, can override any agent or task.

**Goal**: An outcome statement, explicitly *not* a container of work: "Goals sit above projects and issues in the hierarchy: they do not contain code, they do not get 'worked on' directly, and they do not have an execution workspace." Goal fields per the API (`docs/api/goals-and-projects.md`): `title`, `description`, `level` (e.g. `company`/`team`), `status` (`planned | active | achieved | cancelled`), `parentId` (for hierarchy). Goals form a tree via `parentId`; company goals can have sub-goals (team/agent-level). **No metric/target/deadline fields exist on a goal** in the documented schema — only title, description, level, status, parent. There is no numeric progress rollup: "Paperclip does not compute a numerical percentage on goals. The goal's status field is the one authoritative signal." Progress is inferred qualitatively from the mix of linked projects' statuses. Status propagation is manual: "Paperclip does not auto-compute a parent goal's status from its children."

**Goal → Project → Issue chain** (exact quote): `Goal → Project → Issue → Execution workspace → Agent run`. Goals link to Projects (many-to-many: "A project can be linked to multiple goals"); Issues do not link to goals directly — "there is no separate 'assign issue to goal' UI at the issue level" — an issue inherits its goal(s) transitively through its project.

**Project**: groups issues, binds to a repo/cwd, holds its own budget envelope and execution workspace config. Status: `backlog | planned | in_progress | completed | cancelled`. Projects, like goals, have no single "percent complete" field — progress is read off the Issues tab status counts.

**Issue** (= Task, used interchangeably in API/UI): the actual unit of work — title, description, priority, status, assignee, comment thread. Status lifecycle: `backlog → todo → in_progress → in_review → done`, plus `blocked` and `cancelled`. Issues can have sub-tasks (hierarchy). "Atomic checkout": moving an issue to `in_progress` claims exclusive agent ownership, preventing double-work.

**Agents**: "AI employee — a configured role with a specific job, a manager, and a monthly budget." Strict single-manager hierarchy (org chart); every agent reports to exactly one manager except the CEO, which reports to the board.

**Heartbeats**: scheduled execution windows (detail in section 4).

**Approvals**: governance checkpoints — "Strategy approval" (CEO's initial plan, blocking) and "Hire agent approval" are the two beginner-facing types; budget override approvals and other board-level approvals also exist. Approvals can be Approved, Rejected, or sent back for **Revision** (agent resubmits). Approvals "don't expire on their own" — a pending approval blocks the dependent agent indefinitely until a human acts.

**Budgets**: dollar caps at three independent, parallel levels — **company** (overall ceiling), **agent** (per-agent monthly cap), **project** (lifetime cap by default, metric = `billed_cents`). At 80% utilization: warning. At 100%: hard stop — "the agent is automatically paused and no more heartbeats fire" (or the project pauses, independently). All three levels can each independently halt work; none supersedes the others except that a company-level stop blocks everyone.

**Company Package format** (`companies-spec.md`, `agentcompanies/v1-draft`): a filesystem/GitHub-native markdown+YAML-frontmatter spec for portably describing `COMPANY.md`, `TEAM.md`, `AGENTS.md`, `PROJECT.md`, `TASK.md`, `SKILL.md`. This is explicitly a *portability/export* format, not the live runtime data model (which lives in Paperclip's own DB) — "project packages are intended to seed planned work, not represent runtime task state." Notably `TASK.md` supports `recurring: true` for template/recurring tasks, with the actual cron trigger living in a vendor extension `.paperclip.yaml` (`routines.<name>.triggers[].kind: schedule / cronExpression`).

## 2. The CEO Pattern and Delegation Mechanics

**VERIFIED** — `docs/guides/welcome/key-concepts.md`, `docs/guides/org/delegation.md` (paperclip-docs), `docs/guides/board-operator/delegation.md` (paperclip, near-duplicate content), `docs/built-in-agents.md`, `docs/agents-runtime.md` (all paperclip repo).

There is a genuine built-in CEO **pattern**, not a hardcoded CEO binary. Quote: "The CEO agent is always the first agent you create. It's the entry point — once the CEO is running, it creates tasks and can request to hire its own reports." It's an ordinary `claude_local`/`codex_local`/etc. agent whose behavior comes from its `AGENTS.md` instructions file, not special-cased code: "The CEO's delegation behavior is driven by its `AGENTS.md` instructions file... If AGENTS.md is missing or doesn't mention delegation, the CEO won't know to break down goals and assign work." So the "CEO" is a convention/role (first agent, no manager, reports to the board) plus a prompt, enforced by org-chart position, not a distinct agent type in the schema.

Separately there is a **"Built-in Agents"** subsystem (`docs/built-in-agents.md`) — first-party, registry-defined, non-CEO agents provisioned without board-hire-approval, keyed by a stable string (`briefs`, `learning`, and a documented hypothetical `digest`). These are system-utility agents (e.g., a company activity summarizer), not department heads, and are explicitly distinct from the CEO/org-chart hire flow: "Provisioning does not require board hire approval... because built-ins are registry-owned system capacity, not ad hoc hires."

**Delegation flow (exact, from `delegation.md`):**
```
You set a company goal
  → CEO wakes up on heartbeat
  → CEO proposes a strategy (creates an approval for you)
  → You approve the strategy
  → CEO breaks goals into tasks and assigns them to reports
  → Reports wake up (heartbeat triggered by assignment)
  → Reports execute work and update task status
  → CEO monitors progress, unblocks, and escalates
  → You see results in the dashboard and activity log
```
Nothing proceeds past the strategy stage without human approval — this is a hard block, not just a recommendation: from `key-concepts.md`, "Nothing proceeds until you approve this."

**Who creates issues / who assigns / what wakes whom** — directly answers the CLAUDE.md-relevant question of org-chart delegation:
- The CEO (or any manager agent) creates child tasks/issues and assigns them to its reports on its own heartbeat, after strategy approval.
- Assignment itself is a wake trigger: `agents-runtime.md` lists the four wake reasons verbatim: **`timer`** (scheduled interval), **`assignment`** (work assigned/checked out to that agent), **`on_demand`** (manual button/API wakeup), **`automation`** (system-triggered wakeup, used e.g. by built-in agents via `heartbeatService(db).wakeup(agent.id, {source: "automation", ...})`). "If an agent is already running, new wakeups are merged (coalesced) instead of launching duplicate runs."
- Reports execute and post progress as task comments; the CEO's own subsequent heartbeats read those comments to "monitor progress, unblock, and escalate."
- Escalation travels *up* the `reports_to` chain — an agent that cannot resolve something creates/escalates toward its manager, ultimately reaching the board if no agent can act (see delegation-cycle guardrail below).

**Guardrails on agent-to-agent delegation** (VERIFIED, `docs/guides/board-operator/delegation.md`) — these matter directly for an unattended multi-department system:
1. **Paused-assignee refusal**: "Cannot assign work to a paused agent. Assign an invokable agent, leave the issue unassigned, or escalate to a board operator instead." Prevents work silently vanishing into a paused manager's queue.
2. **Delegation-cycle refusal** (`delegation_cycle` conflict code): an agent cannot create a child task assigned back to a still-open ancestor in the same delegation chain — stops A→B→A capability-gap loops. "Complete the remaining work in your own issue, leave the child unassigned, or escalate to a board operator — do not delegate the work back to the agent that delegated it to you." Only counts non-`done`/non-`cancelled` ancestors, and only when the *creator* of the child is the ancestor, not just "the assignee."
3. **Dead escalation path warning**: an amber "Escalation path is paused" banner appears when an agent's manager chain is paused — a real risk pattern after an org import that pauses everyone by default.

Practical implication for the Habib use case: department "managers" (e.g., a Finance/Supply-Chain/Advertising lead under a CEO) are ordinary agents whose delegation quality is entirely a function of prompt engineering in their `AGENTS.md`, not a built-in planning algorithm — there is no separate "goal decomposition" model; it's "the CEO reads its AGENTS.md and decides."

## 3. Proactive Task/Decision Creation for the Human Operator

**VERIFIED** — `docs/guides/day-to-day/approvals.md`, `docs/guides/day-to-day/decisions.md`, `docs/how-to/add-a-human-teammate.md`, `docs/how-to/wire-slack-discord-notifications.md` (paperclip-docs); `docs/guides/agent-developer/handling-approvals.md` (paperclip).

**Yes, agents can create work items for the human, through three distinct mechanisms** (not one unified API), each with different scope:

1. **Formal Approvals** (`POST /api/companies/{companyId}/approvals`, types `hire_agent`, `approve_ceo_strategy`, budget-override, and a generic `request_board_approval`) — for "governed actions that need formal board records, such as hires, strategy gates, spend approvals, or security-sensitive actions." These block the requesting agent's downstream work until resolved. Resolution states: `pending → approved | rejected | revision_requested → resubmitted → pending`. No expiry: "Approvals don't expire on their own... agents that are waiting on it will pause at that point until you take action."

2. **`request_confirmation` interactions** (`POST /api/issues/{issueId}/interactions`) — the documented, explicit alternative for *lighter* in-thread yes/no questions ("Accept this plan?", "Use option A or reject and request changes?") that should NOT be modeled as formal approvals. Bound to a document revision, supports an idempotency key and `supersedeOnUserComment: true` so a later human comment invalidates a stale ask.

3. **Agent-proposed "Decisions"** (the newest, richest surface, per `docs/guides/day-to-day/decisions.md`, dated `paperclip_version: v2026.824.0` — i.e. shipped only ~2 weeks before this evaluation) — "When an agent works out what should happen next but isn't allowed to do it alone, it raises a decision: a short question, an explanation, and up to eight options. Each option spells out exactly what Paperclip would do if you picked it — post a comment, create an issue, change a status, reassign work, clear a blocker, or cancel an issue and everything under it." This is the closest built-in match to "agent creates a task/decision for the human, human approves." Decisions can require human-supplied fields, expire automatically after 7 days by default, detect drift ("1 target changed since this was proposed"), and support **triage** metadata (decide-by: today/this week/whenever/date, snooze, named queues) so a human can manage a large inbox. Dismissal is a recorded "no", distinct from silent expiry, so "agents get honest feedback about which proposals are worth making."

The **Decisions page is the unified human inbox**, merging approvals, blocked issues, agent questions, join requests, failed runs, and budget alerts into one ranked queue — this is functionally the "daily brief"/task list an operator like Rami would use, though it is not literally a scheduled push message.

**How the human sees and answers it**: primarily the **web UI** (Decisions page, Approvals page, per-issue comment threads) and a documented **REST API** (`/api/companies/{companyId}/approvals`, `/api/decisions`, `/api/issues/{issueId}/interactions`) plus a **CLI** (`paperclipai` commands mirror the API 1:1, per `docs/how-to/add-a-human-teammate.md`'s CLI-equivalents pattern). Human teammates (not just the sole board operator) can be invited with `Viewer`/`Operator`/`Admin`/`Owner` roles — relevant to the Habib use case's three human stakeholders (Rami, father, brother) each needing different access.

**Chat/mobile delivery is NOT a first-party feature.** Direct, load-bearing quote from `docs/how-to/wire-slack-discord-notifications.md`: **"Paperclip does not push outbound webhooks today — the routine + agent pair *is* the push."** To get Slack or Discord notifications at all, you must build it yourself: hire a dedicated "notifier" agent, create a scheduled Routine (e.g. every 60s) that wakes it, have the agent poll `GET /api/companies/{id}/approvals?status=pending` and `GET /api/companies/{id}/issues?status=blocked&priority=critical,high`, diff against a manually-persisted "last-seen" cursor (stored as a comment on a dedicated state issue, if using a local CLI adapter with no external KV), and POST formatted Block Kit / embed JSON to a webhook URL you provision on Slack's or Discord's side. There is no Telegram-specific guide, and no bot inline-keyboard approve/reject pattern is documented anywhere in either repo — the guide explicitly frames the *inbound* direction (Slack button click → Paperclip) as unbuilt; the webhook flow described is Paperclip receiving inbound signed triggers (Stripe, GitHub) via "Routines API → Webhook triggers" (`bearer`, `hmac_sha256`, `github_hmac` signing modes), not sending an approve/reject button into a chat app. So a Telegram approval flow with inline Approve/Reject buttons (as specced in the CLAUDE.md architecture) is NOT available out of the box and would need to be hand-built exactly the way the Slack recipe describes, then further extended for inbound button callbacks — real, non-trivial engineering. Only the web UI and the REST/CLI surfaces are native; "mobile" only exists insofar as the web dashboard is responsive, not as a dedicated mobile or chat app.

## 4. Heartbeat Semantics

**VERIFIED** — `docs/guides/agent-developer/heartbeat-protocol.md` (paperclip); `docs/guides/projects-workflow/routines.md`, `docs/how-to/debug-stuck-heartbeat.md` (paperclip-docs).

**The nine-step protocol every agent runs on every wake** (identical text appears in both the standalone heartbeat-protocol doc and the Routines appendix, confirming it is the stable API contract, not draft prose):
1. `GET /api/agents/me` — identity, chain of command, budget.
2. If `PAPERCLIP_APPROVAL_ID` env var is set, resolve that approval's linked issues first.
3. `GET .../issues?assigneeAgentId={id}&status=todo,in_progress,in_review,blocked` — the agent's inbox, priority-sorted.
4. Pick work: `in_progress` first, then `in_review` (only if woken by a comment there), then `todo`; skip `blocked` unless it can unblock it; `PAPERCLIP_TASK_ID` env var (if set) takes priority; if woken by an @-mention, read that thread first.
5. **Checkout** (`POST /api/issues/{id}/checkout` with `X-Paperclip-Run-Id` header and `expectedStatuses`) — this is the atomic-lock mechanism. A conflicting checkout returns `409`; the rule is explicit and repeated twice: **"Never retry a 409"** — the losing agent must pick different work, not spin.
6. Read full issue + comments + ancestors for context.
7. Do the work — "take a concrete action in the same heartbeat... do not stop at a plan unless the issue asked for planning."
8. `PATCH /api/issues/{id}` with the same run-id header to set status (`done`/`blocked`/etc.) and a comment — this is how progress persists **durably across heartbeats**: state lives in the issue's status + comment thread + any documents/work-products, not in agent memory. Session continuity (see adapters section) is a *convenience* on top of this, not the source of truth.
9. Delegate via child issues (`parentId` + `goalId` required) instead of polling.

**Work-in-progress persistence across heartbeats**: two layers — (a) durable, required layer = the issue's status/comments/documents in Supabase-equivalent Postgres, which is what the next heartbeat (possibly a different session, different agent, or after a crash) reads; (b) an optional convenience layer = adapter session resume ("Paperclip stores session IDs for resumable adapters... Next heartbeat reuses the saved session automatically... gives continuity across heartbeats" — `agents-runtime.md`). If the session is stale/looping, the operator can reset it.

**Execution locks**: the checkout mechanism above is the only lock; it is issue-scoped (one issue, one agent, one run at a time) — not a global agent lock. "Atomic checkout... prevents two agents from working on the same task simultaneously."

**What happens if the machine was asleep at heartbeat time** (i.e., missed schedule ticks): governed by **routine catch-up policy**, not per-agent heartbeat logic — quote: "Catch-up policy — what to do about ticks that were missed while the routine or the scheduler was paused. Options: skip the missed windows, or catch up in capped batches (`enqueue_missed_with_cap`)." Default is **skip missed** — a missed tick is simply dropped, not queued. If capped-catchup is chosen, "the scheduler will create up to the configured cap of catch-up runs and then drop the rest" to avoid a flood after a long outage. Concurrency policy (coalesce/skip/always-enqueue) separately governs overlapping ticks while a previous run is still in flight — default is coalesce.

**Wake-reason taxonomy** confirmed exactly as the assignment specified: `timer`, `assignment`, `on_demand`, `automation` (`agents-runtime.md` §2, verbatim). A fifth, narrower reason appears in the debug guide: `finish_successful_run_handoff` — a bounded, single-attempt corrective wake Paperclip issues to the same agent when a run ends without a "disposition" (`done`/`cancelled`/`in_review`-with-reviewer/`blocked`-with-owner/delegated-follow-up). This wake runs on the agent's full/normal model settings (not a cheap recovery profile), reads back the agent's own last report, and is capped at one retry before Paperclip hands the stuck issue to a "recovery owner" instead of looping.

**Design philosophy on timers** (directly relevant to "keep departments working unattended on a schedule"): Paperclip's documented best practice explicitly *discourages* naive per-agent polling timers. Quote: "A new agent ships with timer heartbeats turned off by default. That's deliberate, and it's the setting you should usually keep... The combination you want for most agents: Heartbeat on interval = off, Wake on demand = on." Scheduled/recurring work is meant to live in **Routines** (a first-class scheduled-job object with cron trigger, target agent, and delivery/catch-up policy), which create-and-assign an issue on each fire — the assignment then wakes the agent through the normal `assignment` path. "Pause vs. heartbeat off" are explicitly different states — Pause is a hard stop (blocks all four wake types); heartbeat-off still wakes on assignment/comment/routine/on-demand, "active" on the dashboard.

## 5. Pipelines

**VERIFIED** — `docs/pipelines-tutorial.md` (paperclip repo). Note: this file lives only in the paperclip (not paperclip-docs) repo and reads as an internal/engineering-facing walkthrough rather than a polished user guide — it repeatedly flags itself as **v1, provisional, and still separating "conventions" from "primitives"**: "The walkthrough intentionally labels conventions separately from primitives. Those conventions are future primitive candidates: if they hurt, we want to see exactly where." No `docs/pipelines-tutorial.md` counterpart exists in paperclip-docs, and no user-facing "Pipelines" guide was found there — pipelines appear to be a newer/lower-level primitive than the polished Goals/Projects/Issues/Routines/Decisions surfaces documented for end users.

**What a Pipeline is**: a named, reusable **stage machine** (`paperclipai pipelines create --stages-file ...`) — an ordered list of stages, each with a `kind` (`open`, `working`, `review`, `done`, `cancelled`) and per-stage `config` such as `autoAdvanceOnChildrenTerminal` (parent case auto-transitions once all its child cases reach a terminal stage — a genuine recurring rollup mechanism) and, for `review` stages, `approveToStageKey` / `rejectToStageKey` / `requestChangesToStageKey` / `reviewerKind: "human"`. Work items inside a pipeline are called **cases** (not issues), created via `pipelines ingest` / `ingest-batch`, and cases can be parent/child (`parentCaseId`) and cross-linked with `blockedByCaseKeys` for dependency gating (a transition attempt on a blocked case fails `409 code=blocked`). Cases carry free-form `fields` (JSON) and an optimistic-concurrency `version` (edits require `expectedVersion`, mismatches return `409 code=version_conflict`).

**Do pipelines implement recurring goal-driven workflows?** Partially, and by composition rather than as a single primitive: a **Routine** (schedule or webhook trigger) is what actually fires and creates the recurring "root case" or drafting task on a cadence — e.g. "a real system would start with a release-cut routine... the routine fires on a timer or API trigger and creates an intake issue" and a documented `pipelines set-automation --stage drafting --routine <id>` binding attaches a routine to a specific pipeline stage so that stage's work is populated on a recurring schedule. So the recurring/scheduled half comes from Routines (section 4), and Pipelines supply the **multi-stage workflow-with-gates-and-rollup** half (human review gates, auto-advance on children-terminal, dependency blocking, drift detection when an upstream case changes after downstream work already started — `paperclip pipelines case edit` posts "drift comments on dependent linked work issues"). Together they could model something like "every Monday, spin up this quarter's inventory-review pipeline, auto-roll-up SKU cases to a category case to a company case," but this is a hand-built composition, not a documented off-the-shelf "quarterly goal cadence" template — there is no goal-specific pipeline template in the docs, and the tutorial's own domain example is content publishing (blog/tweet/changelog), not a business-operations domain.

## 6. The `claude_local` and `codex_local` Adapters in Practice

**VERIFIED** — `docs/adapters/claude-local.md`, `docs/adapters/codex-local.md`, `docs/guides/agent-developer/cost-reporting.md` (paperclip repo); `docs/guides/day-to-day/costs.md` (paperclip-docs).

**`claude_local` config fields**: `cwd` (required, absolute path, auto-created), `model`, `promptTemplate` (supports `{{agentId}}`, `{{companyId}}`, `{{runId}}`, `{{agent.name}}`, `{{company.name}}` interpolation), `env` (supports secret refs), `timeoutSec`, `graceSec`, `maxTurnsPerRun` (default 300), `dangerouslySkipPermissions` (**default `true`** — required for headless runs since no human is present to click through permission prompts — this is a real safety-relevant default to flag for the Amazon-writes use case). Instructions come from a separate "managed instructions bundle" (i.e., `AGENTS.md`-equivalent) layered on top of `promptTemplate`; `bootstrapPromptTemplate` is explicitly deprecated.

**Session resume**: Paperclip persists the Claude Code session id between heartbeats and resumes with `--resume`; resume is **cwd-aware** — a changed working directory silently starts a fresh session. **Known, documented adapter bug and its fix** (internal tickets RED-976/RED-978, both linked but not resolvable from outside): a "poisoned `previous_message_id`" failure mode where a malformed on-disk transcript JSONL causes Anthropic's API to permanently 400 on every resume attempt, which — without the implemented guard — would strand the issue forever. The documented mitigation is auto-rotation: on this specific 400, the adapter retries once with a fresh session, best-effort deletes the poisoned transcript file, never persists the poisoned session id, and sets `clearSession: true`. This is a genuine, named production bug class that Paperclip has had to engineer around, evidence the local-CLI-wrapping approach is fragile in exactly the way you'd expect (shelling out to a CLI and parsing its transcript state).

**Skills injection**: `claude_local` symlinks Paperclip skills into a temp dir passed via `--add-dir` (keeps the working directory clean); `codex_local` symlinks into the global `~/.codex/skills` (can collide with the user's own Codex skills directory, though "existing user skills are not overwritten").

**MCP configuration**: not documented as a distinct file path for these two adapters in the files read; skills/instructions are the primary customization surface documented. (Not found: an explicit `mcpServers` config block for `claude_local`/`codex_local` in these two files — see `docs/how-to/add-mcp-server-to-agent.md`, not fully read here — **UNKNOWN** exact schema without reading that file directly, flagged for follow-up.)

**Cost tracking for subscription runs — does NOT report zero.** This directly contradicts a plausible assumption: Paperclip explicitly tracks subscription-backed runs as a distinct **biller** type ("Run-type breakdown: `N api · N subscription` — how many runs went through API-priced calls versus subscription-backed calls") and assigns them a real, non-zero, **estimated** dollar cost: "Paperclip's number for a subscription day is its best guess — **typically derived from the plan price divided by the billing cycle length**. Once the real invoice arrives and is imported, the estimated flag flips off and the number becomes authoritative." So a Claude Pro/Max subscription-backed `claude_local` agent shows up in the cost ledger as an amortized daily/session fraction of the subscription price, not $0.00 and not true per-token API pricing. Paperclip's own guidance: "Prefer subscriptions when usage is predictable... routing through the subscription biller can be cheaper than pay-as-you-go API pricing" — with a **quota-windows** UI (for Anthropic Pro/Max's rolling 5-hour/daily/weekly caps) to check headroom before committing an agent to a subscription.

**Remote/managed-sandbox credential ownership** differs meaningfully between the two adapters and is a real operational gotcha: `claude_local` is **snapshot-owns-auth** for managed sandbox execution (credentials baked into the sandbox image win over the host's), while `codex_local` is **host-owns-auth** (the host's `auth.json`/API key is uploaded and shadows anything already in the sandbox image). An operator moving between the two adapters, or between local and sandboxed execution targets, needs to understand this asymmetry or agents can silently run under the wrong credential (or fail-fast with `401`/`adapter_failed` for Codex's managed-home guard).

**Known limitation flagged as unfinished in the docs themselves**: the "Deferred config-validation warning spec" in `codex-local.md` explicitly documents a **not-yet-implemented** warning for a real risk (running a subscription-authenticated Codex agent against a remote/sandboxed execution target, which can silently share a rotating subscription token across concurrent sandboxes) — the doc says outright, "This section specifies a warning that is not implemented yet," which is unusually candid but also confirms a live gap in the product as documented.

## 7. Multi-Company/Organisation, and the `paperclip-mcp` Server

**VERIFIED** — `packages/mcp-server/README.md` and `packages/mcp-server/package.json` (paperclip repo, published as `@paperclipai/mcp-server` on npm, bin `paperclip-mcp-server`); `docs/administration/company.md` (paperclip-docs); `docs/how-to/add-mcp-server-to-agent.md` (paperclip-docs).

**Multi-company**: one Paperclip instance runs multiple independent Companies side-by-side, switched via a "company switcher" in the sidebar; each Company is its own goal/agent/task/budget boundary (per section 1). This directly matches CLAUDE.md's stated future need for a per-brand/per-tenant boundary ("Add Mode Considerations... New Brand Onboarding... per-tenant isolation"), i.e. a second Amazon brand could be modeled as a second Company on the same instance without forking code — consistent with Paperclip's own stated productization story, though Paperclip's docs don't specifically address cross-company reporting/roll-up (a father/brother wanting one combined view across two brands would need to build that themselves; **UNKNOWN** whether a unified multi-company dashboard view exists).

**`@paperclipai/mcp-server` (`paperclip-mcp-server` binary)** is a real, shipped, first-party package — explicit quote: "This package is a thin MCP wrapper over the existing Paperclip REST API. It does not talk to the database directly and it does not reimplement business logic." It authenticates via `PAPERCLIP_API_URL` + `PAPERCLIP_API_KEY` (+ optional `PAPERCLIP_COMPANY_ID`/`PAPERCLIP_AGENT_ID`/`PAPERCLIP_RUN_ID`), i.e. it's driven by a normal bearer-token API key, not something restricted to running-agent contexts.

**Yes — an external Claude Code session (the human's own, running outside Paperclip) can create goals and issues through this MCP server**, though asymmetrically:
- **Issues**: full first-class support — dedicated tools `paperclipCreateIssue`, `paperclipUpdateIssue`, `paperclipCheckoutIssue`, `paperclipReleaseIssue`, `paperclipAddComment`, etc.
- **Goals**: only **read** tools are named explicitly — `paperclipListGoals`, `paperclipGetGoal`. There is **no** dedicated `paperclipCreateGoal` / `paperclipUpdateGoal` tool in the documented tool surface.
- **The escape hatch closes the gap**: `paperclipApiRequest` is documented as a generic tool "limited to paths under `/api` and JSON bodies... meant for endpoints that do not yet have a dedicated MCP tool," which — combined with the documented REST endpoints `POST /api/companies/{companyId}/goals` and `PATCH /api/goals/{goalId}` (section 1) — means an external agent *can* create/update goals through this server, just not via a purpose-built, schema-validated tool call; it has to construct the raw REST payload itself. Practically this is workable but rougher and more error-prone than the polished issue tools.
- Approvals are also fully covered (`paperclipCreateApproval`, `paperclipApprovalDecision`, `paperclipLinkIssueApproval`, etc.) — meaning an external orchestrator could, in principle, both propose *and* resolve approvals through this one MCP server, which is worth flagging as a governance consideration: the approval gate's strength depends entirely on who holds the API key used by this MCP client, not on any code-level separation between "propose" and "decide" access.

MIT license (`LICENSE` file, confirmed by README's license badge). `CONTRIBUTING.md` describes a structured process (PR template, "Greptile score 5/5", a Discord `#dev` channel for larger changes, dedup-search requirement) indicative of an organized, moderately well-resourced open-source operation rather than a single maintainer repo.

**Open issues — VERIFIED via GitHub web UI**: **~2,200 open issues** at time of writing. Recent-issue themes read off the issue list: adapter/integration problems (ACPX adapter, HTTP adapter config mismatches, credential/billing path changes without notification), auth/access-control gaps (password reset, env-var leakage to spawned agents, DB credential inheritance), deletion/data-integrity bugs (incomplete cascade deletes, orphaned FKs, archived-decision retention failures), and configuration/timeout issues (local-gateway timeouts, doc-vs-actual field name mismatches) — a volume and mix consistent with a fast-moving, widely-used, still-maturing platform rather than a stable/mature one.

**Critical security incident — REPORTED, but well-corroborated across many independent outlets** (TheHackerNews, SecurityWeek, CSO Online, GBHackers, Oasis Security, SC Media, CyberPress, all found via WebSearch; direct article fetch blocked by this session's egress filter for all of them, so treat as REPORTED, not independently verified against primary text): **CVE-2026-41679**, reported CVSS **10.0** (maximum), a **remote code execution** vulnerability affecting network-accessible Paperclip instances in default "authenticated mode." Reported attack chain: an unauthenticated attacker could self-register an account (no email verification required), self-approve a CLI authorization challenge to mint a persistent board-level API credential, then use the **company-import path** (the same "Agent Companies" markdown+`.paperclip.yaml` package format documented in section 1) to import a company containing a maliciously configured `process`-adapter agent, whose configured shell command then executed **as the Paperclip server process** on import/first run. This directly implicates the same `process` adapter and `.paperclip.yaml` vendor-extension mechanism documented as a first-class, intended feature in `companies-spec.md` — i.e., the exact "company package" portability feature this evaluation flagged as attractive for reuse/backup is also the feature that produced a CVSS-10 RCE. **Reported fix**: Paperclip patched in **v2026.416.0** by requiring instance-administrator access for imports that create a new company, and existing-company access for imports into an existing one. Given this session's clone is a shallow fetch of `master` at `v2026.831.1`+ (well past `v2026.416.0`), the specific reported flaw is very likely fixed in current code — but the underlying architecture (config-as-executable-code via `process`/`http` adapters and importable `.paperclip.yaml`) is not eliminated, only gated, so import provenance and reviewer discipline remain load-bearing for safety on any future Paperclip instance the Habib OS might run, especially if it is ever exposed to the network rather than kept fully local/behind a VPN.

**User quality complaints — REPORTED, sourced from WebSearch snippets of secondary blog coverage (freecode.academy, mindstudio.ai, xcloud.host), not independently verified against primary Reddit/HN threads (direct fetch of those aggregator/blog pages was not attempted beyond the search snippet)**: reported Reddit sentiment describes Paperclip in some setups as "performing a lot worse than just using Claude Code," with "bugs and unreliable execution," and a documented anti-pattern: "Paperclip is often chosen when only one agent is needed, and in such cases Paperclip is overhead." A recurring theme across secondary sources is a **coordination-overhead ceiling** — orchestration cost is claimed to outweigh parallelism benefit "somewhere past three to four concurrent agents." This is directly relevant: the Habib use case's three-to-eight department agents (finance, supply chain, advertising, catalog, pricing, customer, compliance, expansion) sits right at or above that reported saturation point.

**Data export path if abandoning it — VERIFIED, and genuinely good.** `docs/guides/power/export-import.md`: a company exports to a **human-readable markdown package** (`COMPANY.md`, `agents/*/AGENTS.md`, `projects/*/PROJECT.md`, `skills/*/SKILL.md`, `tasks/*/TASK.md` + documents, `.paperclip.yaml` for adapter/budget/env-var-name metadata) — the same `agentcompanies/v1-draft` spec from section 1, explicitly designed to be "usable by any agent-company runtime, not only Paperclip." What travels: agent identity/instructions/adapter config/budgets, projects+workspaces, skills, tasks with full comment/document/blocked-by history, routines+triggers, attachments. What does **not** travel (by design): secret values, machine-specific paths, internal DB ids, and — notably — **approvals, cost history, and activity log entries are explicitly left behind** ("these are records of what happened on the source instance rather than configuration"). For a governance-sensitive use case, this means the audit trail itself is NOT portable — only the current-state configuration is; a full audit-history migration or long-term compliance record would need a separate backup strategy (e.g., periodic DB dumps) beyond the documented export flow.

## 9. Gaps Against the Use Case, and What Would Have to Be Built

**Confirmed by search — VERIFIED**: neither repo contains any Amazon, SP-API, Shopify, or general e-commerce-specific adapter, skill, or built-in agent. The only third-party-integration-shaped primitives are generic: the MCP-attachment mechanism (section 7), a provider-agnostic `docs/specs/external-task-protocol.md` (draft v1, for Linear/Jira/Asana/Notion/Trello/GitHub-Issues sync — not e-commerce), and the general `process`/`http` adapters. Every worked example in the docs (pipelines-tutorial.md's content-production pipeline, the GitHub-MCP worked example, `AGENTS.md` samples) is software-development or content-marketing shaped. Paperclip is a **domain-agnostic orchestration/governance layer**, not an e-commerce operations product — everything Amazon-specific (SP-API sync, inventory math, PPC bid logic, pricing rules, the L1 business-rule constants in CLAUDE.md) would have to be written from scratch as agent instructions, skills, and tool integrations exactly as much work as building it on the existing bespoke stack, plus the added cost of learning Paperclip's object model.

**Gap 1 — Chat/mobile delivery (Telegram, or Slack/Discord with inline approve/reject).** Not native (section 3). The documented pattern for even Slack/Discord is a hand-rolled routine+notifier-agent+cursor-diffing scheme that only pushes *notifications*, not two-way inline approve/reject — inbound webhook signing exists for other services (Stripe/GitHub) posting *into* Paperclip, but nothing documented lets a chat button *resolve* a Paperclip approval. Building a real Telegram daily-brief + inline-approve flow (as CLAUDE.md's architecture specifies) means building: (a) the outbound notifier (following the Slack/Discord recipe, adapted to Telegram's Bot API), and (b) a net-new **inbound** path — a small webhook receiver that turns a Telegram callback-query into a `POST /api/approvals/{id}/decision`-equivalent call, using the escape-hatch `paperclipApiRequest` MCP tool or the plain REST API with a service credential. This is a real, non-trivial custom service, not a config option — likely comparable in effort to the bespoke Telegram bot layer CLAUDE.md's own architecture already designs (Layer 6 in the existing plan), so Paperclip does not save this work.

**Gap 2 — Typed request/goal schema with metrics, targets, deadlines.** Goals have only `title`, `description`, `level`, `status`, `parentId` (section 1) — no numeric target, no deadline field, no owner field, and explicitly no progress percentage ("Paperclip does not compute a numerical percentage on goals"). CLAUDE.md's architecture wants goals with quantifiable KPIs (e.g., days-of-supply thresholds, ACOS targets, margin floors) — these would have to be encoded as free-text in the goal description, or as structured `fields` on Pipeline **cases** (which do support arbitrary JSON `fields` with optimistic versioning — the closest built-in typed-data primitive, but scoped to the newer, provisional Pipelines system, not Goals) or externally in Supabase and cross-referenced by convention only. There is no first-class "quarterly OKR with target/actual" object.

**Gap 3 — Amazon-writes "hands" / executor.** CLAUDE.md's own architecture already has exactly the right pattern (a separate Executor service, the only code with SP-API write creds, watching an approvals table) — Paperclip does not remove the need for this; at best, Paperclip's `approval_requests`-equivalent (its own Approvals/Decisions objects) could *replace* the bespoke Supabase `approval_requests` table as the governance record, but the actual SP-API-calling Executor daemon would still need to be written and run exactly as designed — most naturally as a `process`- or `http`-adapter "agent" (or a plain script triggered by a Routine or webhook) that polls Paperclip's approvals API and calls SP-API on approval, mirroring the existing design almost exactly. Net effect: Paperclip can *host the front two-thirds* (agents, goals/projects/issues, approvals, budgets, dashboard) but the safety-critical execution boundary still has to be hand-built, same as today.

**Gap 4 — Git-markdown state / typed schema durability doubts.** Issue/task state (per the heartbeat protocol, section 4) is durable Postgres rows (status, comments, documents) — not git-markdown as CLAUDE.md's "one source of truth" principle for a knowledge layer implies for Mem0/wiki content. The Company Package format (section 1) is markdown, but is explicitly a **portability/export snapshot**, not the live runtime store — "project packages are intended to seed planned work, not represent runtime task state." So Paperclip does not give CLAUDE.md's Mem0 knowledge-compounding layer (observations → patterns → playbooks, wiki generation) any native equivalent at all: there is no vector memory, no fact-extraction/dedup pipeline, and no generated wiki-page store built into Paperclip. The closest analogues are Skills (reusable instruction bundles, human-authored, not agent-learned) and the `learning` built-in agent stub named in `built-in-agents.md` ("Maintains reusable company learning from completed work and recurring patterns" — but this is a one-line registry description, not a documented, working knowledge-compounding subsystem; **UNKNOWN** how mature or functional the `learning` built-in actually is beyond its registry entry). Replacing CLAUDE.md's entire Layer 3 (Mem0 + pgvector + three-tier promotion + wiki compiler) is squarely **not covered** by Paperclip and would need to be built exactly as CLAUDE.md already designed, run as one or more Paperclip agents/routines that read/write the same Mem0 store.

**Gap 5 — Coordination-overhead risk at the target team size.** Per section 8's REPORTED user sentiment, orchestration overhead is claimed to dominate past 3–4 concurrent agents. The Habib use case wants coverage of finance, supply chain, advertising, catalog, pricing, customer, compliance, and expansion — 8 domains. Even collapsed under a CEO + 3-4 department-head agents (mirroring the existing 3-agent CLAUDE.md design), this sits at the upper edge of, or past, the reported comfortable zone, and the guardrails documented in section 2 (delegation-cycle detection, paused-assignee refusal, escalation-path-paused banner) exist precisely because this failure mode is real and anticipated by Paperclip's own team, not hypothetical.

**What would NOT need to be rebuilt** — to be fair, several real things transfer cleanly: the governance/approval gate model (arguably more mature than a bespoke `approval_requests` table — revision cycles, decision drift-detection, triage/snooze), the CEO→department delegation pattern and its documented org-chart guardrails, budget enforcement at three levels, a working dashboard/UI/CLI/REST-API/MCP surface out of the box, session-persistent Claude Code/Codex adapters with real (if imperfect) cost tracking including subscription-plan amortization, scheduled Routines with cron/webhook triggers and sane catch-up/concurrency defaults, and a clean human-readable export format for backup/migration.
